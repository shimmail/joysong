# 客服消息系统开发文档

> 模块路径：`joysong-server/src/main/kotlin/com/joysong/server/cs/`
> 复用基础设施：`joysong-server/src/main/kotlin/com/joysong/server/dm/`
> Android 端：`joysong-app/src/main/java/com/joysong/app/`

---

## 一、功能概述

客服实时消息通信功能，允许用户通过 App 与平台客服进行即时聊天。核心设计思路是**复用 DM（私信）基础设施**，以 `CS_ADMIN` 作为客服方虚拟用户 ID，避免新建独立的消息表和会话表。

### 1.1 端点隔离

| 端 | API 前缀 | 说明 |
|----|----------|------|
| 用户端 | `/api/cs/*` | 用户创建会话、发送消息、查看历史、标记已读 |
| 管理端 | `/api/admin/cs/*` | 客服回复用户消息、查看会话列表 |

两端共享同一张 DM 表（`dm_conversations` + `dm_messages`），通过 `CS_ADMIN` 虚拟用户 ID 区分客服会话与普通私信。

### 1.2 与 AI 聊天的隔离

CS 角色在 `AiAgentViewModel` 中有独立的会话管理、消息加载、发送和轮询逻辑，与 BESTIE / CONSULTANT 的 AI LLM 聊天完全隔离，互不干扰。

## 二、后端架构

### 2.1 控制器：`CsController`

| 端点 | 方法 | 说明 |
|------|------|------|
| `POST /api/cs/conversations` | `getOrCreateConversation` | 创建或获取用户与客服的会话 |
| `GET /api/cs/conversations` | `listConversations` | 获取用户的客服会话列表 |
| `POST /api/cs/conversations/{id}/messages` | `sendMessage` | 用户发送消息 |
| `GET /api/cs/conversations/{id}/messages` | `listMessages` | 获取消息历史（支持 `limit` 参数，默认 50） |
| `PUT /api/cs/conversations/{id}/read` | `markAsRead` | 标记客服消息已读 |

所有端点均需认证（`Authentication`），通过 `SecurityConfig` 中配置 `/api/cs/**` 规则放行。

### 2.2 服务层：`CsService`

**会话创建逻辑：**
- `userA = minOf(userId, CS_ADMIN)`，`userB = maxOf(userId, CS_ADMIN)`，与 `DmService` 保持一致的排序规则
- 优先查找已有会话，不存在时创建新的 `DmConversationEntity`
- 使用 `DataIntegrityViolationException` 捕获并发创建冲突

**消息发送逻辑：**
- 校验消息内容非空且不超过 5000 字符
- 校验会话归属权（`userAId` 或 `userBId` 包含当前用户）
- 创建 `DmMessageEntity`（`messageType = "TEXT"`）
- 更新会话摘要（`lastMessage` + `lastMessageAt`）
- 增加 `CS_ADMIN` 侧的未读计数
- 通过 `NotificationService` 推送通知给客服（`type = "DM_NEW"`）

**标记已读逻辑：**
- 批量将 `CS_ADMIN` 发来的未读消息标记为已读
- 将用户侧的未读计数归零

**消息查询逻辑：**
- 按 `createdAt` 降序查询后 `reversed()` 返回升序结果
- `limit` 参数限制在 1~100 范围内

### 2.3 DTO：`CsDtos`

```kotlin
data class CsConversationResponse(
    val id: String,
    val userAId: String,
    val userBId: String,
    val lastMessage: String?,
    val lastMessageAt: String?,
    val unreadCount: Int,
    val createdAt: String,
    val updatedAt: String
)

data class CsMessageResponse(
    val id: String,
    val senderId: String,
    val senderName: String,  // CS_ADMIN 显示"平台客服"，其他显示用户昵称
    val content: String,
    val messageType: String,
    val isRead: Boolean,
    val createdAt: String
)

data class CsSendMessageRequest(val content: String)
```

### 2.4 数据模型复用

客服功能不新建数据库表，完全复用 DM 基础设施：

| 表 | 说明 |
|----|------|
| `dm_conversations` | 会话表，客服会话的 `userAId` 或 `userBId` 之一为 `CS_ADMIN` |
| `dm_messages` | 消息表，`senderId` 为实际发送者（用户 ID 或 `CS_ADMIN`） |

### 3.4 轮询机制

`AiAgentViewModel` 中 CS 角色采用 **10 秒轮询** 策略拉取新消息：
- 进入客服聊天页面时启动轮询
- 每 10 秒调用 `GET /api/cs/conversations/{id}/messages` 获取最新消息
- 页面退出时停止轮询
- 与 BESTIE / CONSULTANT 的 AI 聊天使用不同的通信机制

### 3.5 消息软删除机制

消息卡片采用 **软删除** 策略，统一以 `chatDeletedAt` 时间戳作为唯一删除来源：

- `MessageCenter` 中所有会话卡片统一使用 `chatDeletedAt` 字段判断是否已删除
- 当收到新消息时，`updateAiCardFromSession()` 和 `upsertDmCard()` 会自动清除 `chatDeletedAt`，恢复已删除的卡片
- 已移除旧版 `deletedIds` 双轨机制，避免状态不一致

### 3.6 红点未读数全局轮询

`MessageUnreadManager` 提供全局 **15 秒轮询** 机制，替代原先 `HomeViewModel` 中的 60 秒本地轮询：

- `JoysongApp.onCreate()` 启动全局轮询
- 所有页面共享同一轮询源，避免重复请求
- `HomeViewModel` 已移除本地轮询逻辑

## 五、架构决策说明

### 5.1 为什么复用 DM 表而非新建客服表

- 客服消息本质上是一对一即时通信，与 DM 私信的数据模型完全一致
- 复用 `dm_conversations` + `dm_messages` 表避免冗余的表结构和 Repository 层代码
- 通过 `CS_ADMIN` 虚拟用户 ID 区分客服会话与普通私信，查询时 `filter` 即可隔离

### 5.2 为什么用 `CS_ADMIN` 作为虚拟用户 ID

- 统一管理端客服回复入口，所有客服消息的 `senderId` 均为 `CS_ADMIN`
- 避免为每个客服人员创建独立账户，简化权限管理
- 消息展示时 `CS_ADMIN` 统一显示为"平台客服"

### 5.3 CS 角色与 AI 角色的隔离策略

`AiAgentViewModel` 根据角色类型（CS / BESTIE / CONSULTANT）走完全不同的通信链路：

| 角色 | 通信方式 | 数据源 |
|------|----------|--------|
| CS（客服） | REST API + 轮询 | `CustomerServiceRepository` |
| BESTIE（闺蜜） | AI LLM 流式响应 | `AiRepository` |
| CONSULTANT（咨询师） | AI LLM 流式响应 | `AiRepository` |

## 八、变更日志

### v2 — 2026-08-02：消息系统多项优化与 Bug 修复

#### 1. "用户dmin"角色泄漏修复

**问题：** DM 会话列表中出现了 `CS_ADMIN` 客服会话，导致用户看到名为"用户dmin"的异常联系人。

**修复方案：**
- 后端 `DmService.getConversations()` 添加过滤条件，排除 `CS_ADMIN` 参与的会话
- Android `MessagesViewModel` DM 循环中跳过 `CS_ADMIN` 会话
- `DmChatViewModel` fallback 命名逻辑移除 `takeLast(4)` 截断，避免产生无意义名称
- `MessageCenter` 新增 `removeDmCardIfExists()` 方法，主动移除误入的 CS_ADMIN 卡片

#### 2. 消息卡片软删除机制统一

**问题：** 旧版使用 `deletedIds` 列表和 `chatDeletedAt` 双轨机制，导致删除状态不一致。

**修复方案：**
- `MessageCenter` 统一使用 `chatDeletedAt` 时间戳作为唯一删除来源
- `updateAiCardFromSession()` 和 `upsertDmCard()` 收到新消息时自动清除 `chatDeletedAt`，恢复卡片
- 移除旧版 `deletedIds` 双轨机制

#### 3. 删除卡片后进入对话页消息不显示

**问题：** 用户删除消息卡片后，再次进入对话页面时消息列表为空。

**修复方案：**
- `AiAgentViewModel.loadMessages()` 开头清除 `deletedAt` 标记
- `DmChatViewModel.loadMessages()` 开头清除 `deletedAt` 标记

#### 4. CS 卡片未读数不显示

**问题：** 客服消息卡片的未读数红点始终为 0。

**修复方案：**
- `MessageCenter.updateAiCardFromSession()` 新增 `unreadCount` 参数
- `MessagesViewModel` 传递 `conv.unreadCount` 到 MessageCenter
- `AiAgentViewModel.startCsPolling()` 轮询时同步更新 MessageCenter 卡片的未读数

#### 5. 红点实时显示优化

#### 6. AI 聊天单条消息删除后端 API（保留未启用）

- 后端新增 `ChatService.deleteMessage()` 方法
- 后端新增 `ChatController` `DELETE /api/chat/messages/{id}` 端点

### v3 — 2026-08-02：未读计数逻辑修复（仅保留最新消息数）

**问题：** 未读消息计数会累计历史消息（包括已读消息），而非仅显示最新消息的未读数。

**修复方案：**

- **后端** `CsService.getConversations()`：用 JOIN 查询计算未读数，仅统计 `is_read = FALSE AND sender_id != user_id` 的最新消息
- **后端** `AdminCustomerServiceService.getConversations()`：同样修复，使用 LEFT JOIN + COUNT 精确查询未读数
- **Android 端** `CustomerServiceRepository`：Mock 模式的未读计数已同步修正为仅显示最新消息数
