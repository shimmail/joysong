# 专业身份工作台与会话展示身份设计

## 背景

当前 Flutter 客户端将“身份认证”和“专业管理”作为两个并列入口。身份中心能够展示医生、咨询师、机构法人等认证状态，但系统没有“当前工作身份”这一概念；专业管理中心只按服务端返回的能力展示入口。消息系统则以两个用户 ID 唯一确定私信会话，并从账号资料解析头像和名称，因此同一账号的普通用户、医生和咨询师形象无法在会话中区分。

本设计在不改变登录账号和基础鉴权主体的前提下，引入专业工作台、独立职业档案和会话展示身份。第一阶段不改变整个 App 的主导航，只在身份与专业管理范围内切换工作上下文。

## 目标

1. 同一账号可以拥有普通用户、医生、咨询师和机构等多个身份。
2. 个人资料与各职业档案相互独立，头像、名称和公开信息不会串用。
3. 用户可在“身份与工作台”中选择当前工作身份，并看到对应能力和待办。
4. 普通用户从职业详情发起咨询时，咨询绑定具体职业档案，而非仅绑定登录账号。
5. 消息列表、聊天页头像和资料跳转按会话展示身份呈现；同一用户 ID 的不同职业身份保持可见区分。
6. 服务端始终是身份状态、档案归属和管理权限的唯一可信来源。

## 非目标

- 第一阶段不根据身份重构 App 全部首页、底部导航和普通用户功能。
- 不允许客户端根据 `DOCTOR` 等字符串自行推导管理权限。
- 不合并账号资料与职业资料。
- 不把认证材料暴露到公开档案、消息或公共图片接口。
- 不在本阶段重做全部医生、咨询师和机构业务页面。

## 核心概念

### 账号主体

`UserAccount` 是登录、鉴权、推送和消息投递的主体，一个自然人只需登录一个账号。

核心字段：

- `userId`
- 手机号、邮箱和登录安全信息
- 普通昵称和个人头像
- 普通用户个人资料

### 职业档案

职业档案是公开展示和专业服务的主体。不同档案可拥有独立头像、名称、简介、机构关系和服务配置。

- `DoctorProfile(profileId, ownerUserId, ...)`
- `ConsultantProfile(profileId, ownerUserId, ...)`
- `InstitutionProfile(profileId, managers, ...)`

职业头像创建时可继承个人头像作为初始值；之后两者独立维护。修改个人头像不能自动覆盖已有职业头像。

当前医生档案主键虽然等于认证用户 ID，客户端和新接口仍必须同时表达 `profileType + profileId`，不得依赖两者永远相等。

### 工作身份

工作身份表示当前专业管理上下文，不是新的登录账号，也不是新的权限来源。

```text
WorkspaceSelection
- type: USER | DOCTOR | CONSULTANT | INSTITUTION
- profileId: 对应账号或职业档案 ID
```

普通用户身份始终存在。只有状态为已通过且服务端确认当前账号可管理的职业档案才能被选为工作身份。

### 会话展示身份

消息收发与展示采用不同标识：

```text
ConversationParticipant
- accountUserId: 鉴权、推送和消息归属
- presentationType: USER | DOCTOR | CONSULTANT | INSTITUTION
- presentationId: 用户或职业档案 ID
- displayNameSnapshot
- avatarSnapshot
- identityBadgeSnapshot
- profileRouteSnapshot
```

`accountUserId` 可以相同，但 `presentationType + presentationId` 不同时，消息页面必须视为不同展示身份。

## 信息架构与页面设计

### 我的页面

保留顶部个人头像和普通昵称，仅代表账号个人资料。将现有“身份认证”和“专业管理”合并为一个“身份与工作台”入口。

入口摘要显示：

- 当前工作身份的头像、名称和身份标签
- 已认证身份数量或审核中提示
- “切换工作台”操作

普通用户不应因为获得职业身份而失去原有个人页、订单、日记和收藏入口。

### 身份与工作台页面

页面分为三段：

1. 当前工作身份卡片：显示当前头像、名称、身份标签和管理范围。
2. 可用工作台：普通用户及所有已通过认证、可管理的职业档案。
3. 身份申请与状态：审核中、被拒绝、已撤销和可申请身份。

身份项状态：

- 已选中：显示明确选中标记，点击不重复请求。
- 可切换：点击后向服务端重新校验上下文。
- 审核中：禁用切换，展示预计动作“查看申请”。
- 被拒绝：禁用切换，展示审核意见和“重新申请”。
- 已撤销：禁用切换，解释专业入口已关闭。
- 校验失败：保留原工作身份并展示错误，不进入半切换状态。

### 专业工作台

切换成功后进入对应工作台。工作台标题、头像和功能按选中的 `profileType + profileId` 展示，但功能列表仍来自服务端能力上下文。

- 医生：职业资料、咨询、订单、文章和机构关系等已授权能力。
- 咨询师：职业资料、咨询、客户和机构关系等已授权能力。
- 机构：机构资料、成员、项目、订单和内容等已授权能力。
- 普通用户：返回普通个人中心，不展示专业管理能力。

第一阶段允许尚未接入的功能显示为“即将开放”，但必须与可操作入口视觉区分，不能使用可点击卡片后再弹出占位提示。

### 消息列表与聊天页

消息列表以对方的会话展示身份呈现头像、名称和身份标签。聊天页标题和对方消息头像使用同一展示身份。

点击头像或名称的跳转规则：

| 展示身份 | 跳转目标 |
| --- | --- |
| `USER` | 普通用户主页 |
| `DOCTOR` | 医生公开详情 |
| `CONSULTANT` | 咨询师公开详情 |
| `INSTITUTION` | 机构公开详情 |

职业人员自己的消息工作台仅显示归属于当前职业档案的专业咨询；普通身份消息与其他职业身份消息不混合。

## 咨询流程

普通用户从医生、咨询师或机构公开详情发起咨询：

1. 用户点击“立即咨询”。
2. 客户端提交目标 `providerType + providerProfileId`，不直接提交对方账号 ID 作为业务目标。
3. 服务端验证档案可见、认证有效且允许咨询，并解析实际接收账号。
4. 服务端创建或返回该服务范围内的咨询会话。
5. 客户端跳转 `/consultations/{consultationId}`。

建议的咨询会话业务键至少包含：

```text
customerUserId
providerType
providerProfileId
scopeType
scopeId
```

`scopeType + scopeId` 用于区分一次性咨询、订单咨询或项目咨询。不能继续仅以两个用户 ID 唯一确定会话，否则同一账号的医生和咨询师咨询会错误合并。

## 服务端接口与鉴权

### 身份与工作台上下文

新增或扩展服务端响应：

```text
GET /api/identity/workspaces
```

返回当前账号可见的所有工作身份、状态、展示摘要和是否可切换。普通用户工作台始终存在。

```text
GET /api/management/context?type=DOCTOR&profileId=...
```

服务端验证：

- 当前账号是否拥有或被授权管理该档案；
- 认证状态是否仍然有效；
- 档案是否停用或被撤销；
- 每项能力和数据范围是否允许。

客户端可以本地保存最近选择作为启动偏好，但每次进入专业工作台必须重新校验。校验失败时回退普通用户工作台，并给出原因。

### 会话接口

创建会话请求改为职业目标：

```text
POST /api/dm/conversations
{
  "targetType": "DOCTOR",
  "targetProfileId": "...",
  "scopeType": "CONSULTATION",
  "scopeId": "..."
}
```

会话响应直接返回双方 `ConversationParticipant`，Flutter 客户端不再额外按 `userId` 猜测头像和名称。

发送消息仍以登录账号鉴权。服务端根据会话参与者和当前工作权限决定是否允许发送，客户端传入的展示身份不能替代权限校验。

## 快照与资料更新规则

会话创建时保存展示快照，保证历史咨询和订单语义稳定。会话列表可以同时返回当前档案展示信息和创建时快照：

- 活跃会话默认展示当前职业头像与名称。
- 档案被删除、隐藏或撤销时回退快照，并标注“身份已失效”。
- 历史订单、支付记录和正式咨询凭证始终使用交易发生时快照。
- 修改职业资料不能改变会话绑定的 `presentationId` 和跳转类型。

## 状态管理

Flutter 新增独立的 `WorkspaceController`，职责仅包括：

- 加载工作身份列表；
- 保存当前选择；
- 请求服务端校验选中身份；
- 暴露切换中、成功、失败和回退状态；
- 在认证状态变化后刷新列表。

`IdentityController` 继续负责认证申请和材料；`ManagementController` 负责所选工作身份的能力上下文。三者通过明确参数协作，不共享可变的隐式全局角色字符串。

消息模块以服务端返回的 `ConversationParticipant` 构建 `MessagingPeer`。`MessagingPeer.id` 应从单一用户 ID 扩展为展示身份引用，头像点击回调携带完整 `presentationType + presentationId`。

## 错误处理与安全

- 切换期间禁用重复切换，并在目标身份行显示进度。
- 切换失败保留原工作身份和原页面数据，不清空有效上下文。
- 身份被撤销或权限变化时，服务端拒绝操作；客户端刷新工作台并回退普通用户。
- 职业资料接口不得返回认证材料、证件号码和私有文件 URL。
- 会话创建不能由客户端指定实际接收账号，必须由服务端从职业档案解析。
- 相同 `accountUserId` 不能被客户端用来合并不同职业会话。
- 推送载荷携带 `conversationId`，客户端进入会话后再读取服务端确认的展示身份和跳转目标。

## 数据迁移

1. 为咨询师建立与医生对等的独立职业档案和公开详情。
2. 为现有 DM 会话增加双方展示身份字段和服务范围字段。
3. 旧普通私信迁移为双方 `presentationType = USER`。
4. 能从订单或咨询记录可靠识别职业目标的旧会话迁移为对应职业身份；无法可靠识别的保持普通私信，不做猜测。
5. 新增包含展示身份和服务范围的唯一约束，停止仅按两个用户 ID 去重。
6. 迁移期间响应兼容旧字段，客户端完成升级后再移除旧的 peer 查询路径。

## 测试策略

### 服务端

- 同一账号可列出普通、医生和咨询师工作身份。
- 未认证、被撤销或不属于当前账号的档案不能进入工作台。
- 切换上下文不会扩大服务端能力范围。
- 同一对账号的医生咨询和咨询师咨询生成不同会话。
- 创建会话时服务端忽略或拒绝伪造的接收账号和展示资料。
- 档案撤销后不能继续以该职业身份发送新消息。
- 旧普通私信迁移后仍可访问。

### Flutter

- 我的页面正确区分个人资料和当前工作身份摘要。
- 工作台列表覆盖加载、空态、审核中、拒绝、撤销、切换中和失败回退。
- 切换医生、咨询师和机构身份后仅显示服务端授权能力。
- 同一 `userId` 的不同 `presentationId` 在消息列表显示不同头像、名称和标签。
- 点击不同展示身份分别进入正确的用户、医生、咨询师或机构详情。
- 当前工作身份仅筛选相应专业咨询，普通私信不丢失。
- 大字体、窄屏、深色模式、中英文和读屏语义通过组件测试及人工验证。

## 分阶段交付

### 第一阶段：模型与工作台

- 服务端工作身份列表和按档案校验的管理上下文。
- Flutter“身份与工作台”入口、切换器和专业工作台标题。
- 个人资料与职业资料入口分离。

### 第二阶段：咨询与消息展示身份

- 会话参与者展示身份、职业目标建会话和资料跳转。
- 消息列表按当前工作身份筛选专业咨询。
- 旧会话兼容与迁移。

### 第三阶段：职业工作台能力

- 逐步接入医生、咨询师和机构的真实管理功能。
- 根据业务验证结果再评估是否扩展为全 App 工作模式。

## 验收标准

- 用户可以明确知道当前处于哪个工作身份，并安全切回普通用户。
- 个人头像与各职业头像可独立维护。
- 服务端拒绝未授权的工作身份和职业档案访问。
- 同一用户 ID 的医生、咨询师和普通身份在消息页面显示不同头像、名称、标签与跳转目标。
- 普通用户从职业详情发起咨询后直接进入绑定该职业档案的会话。
- 身份撤销、网络失败和权限变化不会产生半切换状态或错误的数据范围。
- 新增服务端和 Flutter 自动化测试覆盖核心成功与失败路径。

## 当前审查限制

本设计基于当前仓库代码、数据流和测试覆盖审查。当前环境未能从 PATH 调用 Flutter SDK，且没有可用的已登录应用浏览器会话，因此尚未取得符合审查流程要求的运行时页面截图。实施阶段必须在可运行的 Flutter 环境中补充当前页面与改造后页面的同尺寸截图、窄屏和大字体检查，不能仅以组件测试替代视觉验收。

## 资质核验系统扩展

### 第一阶段核验策略

项目当前没有医师电子注册、医疗机构登记或企业登记等官方接口的调用权限。第一阶段采用“人工交叉核验、证据留档、适配器隔离”的实现：审核人员通过官方公开查询渠道完成核验，系统保存查询渠道、查询时间、结果摘要、审核人员及私有证据。未来取得接口权限后新增自动核验适配器，不改变申请、证照、审核和职业档案模型。

人工核验不等于仅查看申请人上传的图片。每个法定或平台必查项目必须存在独立核验记录，必要核验项未全部通过时，服务端禁止批准申请。

### 服务端版本化认证规则

新增规则接口：

```text
GET /api/identity/verification-rules
```

响应至少包含：

- `schemaVersion`：规则版本；
- 身份代码、名称和非医疗身份标记；
- 字段代码、类型、标签、长度、格式和是否必填；
- 材料类型、数量约束、文件限制和有效期要求；
- 字段间一致性规则；
- 必需人工核验项；
- 复验周期及 90、30、7 天预警配置。

Flutter 根据规则渲染申请表单和上传项，只保留通用字段组件及安全的即时校验，不再维护医生、咨询师和机构三套静态规则。提交请求携带 `schemaVersion`。规则已变化时，服务端拒绝旧版本提交并返回新版本提示，客户端刷新规则、保留仍兼容的草稿字段并要求用户重新确认。

规则历史必须可追溯。既有申请继续引用提交时的规则快照，审核批准时同时执行当前生效的安全底线；若新规则增加必要材料，申请进入 `NEEDS_MORE_INFO`，不能静默批准。

### 结构化证照

新增 `identity_credentials`，用于保存证照事实而非仅保存上传文件：

```text
identity_credentials
- id
- application_id
- owner_user_id
- role_code
- credential_type
- credential_number
- holder_name
- issuing_authority
- issued_at
- expires_at
- status
- source_file_id
- created_at
- updated_at
```

`credential_number` 按证照类型标准化后存储，并建立防止同一有效证照被无关账号重复占用的约束或冲突审核机制。敏感号码在普通响应、日志和管理列表中默认脱敏，原文仅允许最小权限审核流程访问。

证照状态至少包括 `PENDING_VERIFICATION`、`VALID`、`EXPIRED`、`SUSPENDED` 和 `REVOKED`。没有明确到期日的证照仍需设置平台复验期限，不能永久有效。

### 核验证据与审核事件

新增 `identity_verification_checks`：

```text
identity_verification_checks
- id
- application_id
- credential_id
- check_type
- provider_code
- result
- checked_by
- checked_at
- evidence_source
- evidence_file_id
- evidence_summary
- effective_until
- created_at
```

`evidence_file_id` 指向私有文件，不得转移到公开图片或职业主页。审核人员需要记录实际查询的官方渠道和可复核摘要；只填写“已查看”不能视为有效证据。

新增不可变 `identity_audit_events`，记录申请提交、补件、开始审核、核验结果、批准、拒绝、暂停、到期、撤销和恢复。事件记录操作者、原因、关联规则版本及前后状态，不允许业务接口修改历史事件。

### 可插拔核验适配器

服务端定义统一端口：

```text
VerificationProvider
- verifyIdentityDocument(request)
- verifyDoctorRegistration(request)
- verifyInstitutionRegistration(request)
- verifyBusinessRegistration(request)
```

第一阶段实现 `ManualVerificationProvider`。它不伪造自动查询结果，而是校验审核人员是否提交了完整的人工核验证据，并将标准化结果写入核验记录。

未来自动 provider 返回相同的标准结果：`PASSED`、`FAILED`、`INCONCLUSIVE` 或 `UNAVAILABLE`。自动服务不可用时默认不放行；可以转人工核验，但必须留下从自动失败转人工的事件和原因。

### 标识号码校验

服务端负责最终校验，Flutter 仅提供即时提示。

- 居民身份证：规范化 18 位号码，验证出生日期、顺序码及 GB 11643 校验位；兼容其他证件类型时必须显式选择类型并使用对应规则，不能继续用统一的 6 至 30 位字母数字正则。
- 统一社会信用代码：规范化 18 位代码，验证字符集、登记管理部门代码、机构类别代码和校验位。
- 医师资格证、医师执业证及医疗机构执业登记号：使用独立字段和可配置格式规则；格式校验只负责发现明显错误，不能替代人工官方查询。
- 手机号：按产品支持地区采用显式国家或地区代码和号码规则。

批准时重新执行所有格式、唯一性和一致性校验，不能信任申请提交阶段的结果。

### 一致性规则

必要一致性至少包括：

- 身份证姓名与申请真实姓名一致；
- 医师资格、执业注册持有人与申请人一致；
- 医师执业机构、地点、类别和范围与开放能力一致；
- 营业执照名称、统一社会信用代码、法定代表人与申请信息一致；
- 医疗机构许可名称、地址、主体和营业执照可解释地对应；
- 医疗美容诊疗科目与机构准备发布的项目范围一致；
- 非法人经办人的授权主体、目标机构、权限范围和有效期一致；
- 证照原件、OCR 结果、用户录入和人工查询结果发生冲突时必须转人工处理，不能自动选择其一。

一致性比较采用标准化值并保存原始值和比较结果。名称简称、历史地址或行政区划变更等不能由字符串模糊匹配自动放行，应由审核人员记录解释。

### 医生核验规则

医生申请需要：

- 本人实名身份；
- 医师资格信息；
- 当前医师执业注册状态；
- 执业类别、执业范围、执业地点和主要执业机构；
- 医疗美容主诊备案状态、专业类别和备案机关；
- 对应机构的有效医疗机构许可和医疗美容诊疗科目；
- 发证机关、签发日期、有效期或下次平台复验日；
- 人工官方查询的核验证据。

普通执业医师认证与医疗美容主诊能力分开。缺少医美主诊备案时可以保留符合规则的医生档案，但不能展示“医美主诊医师”标签，也不能开放需要该资质的能力。

审核通过时创建或更新医生档案，并只建立已核验的执业机构关系。申请中填写的机构名称不能直接生成已批准的 `doctor_institutions` 关系。

### 咨询师核验规则

咨询师定位为“咨询顾问（非医师）”，不是法定医疗执业身份。新增独立 `consultant_profiles`：

```text
consultant_profiles
- id
- owner_user_id
- display_name
- avatar
- bio
- specialties
- institution_id
- authorization_expires_at
- is_medical_practitioner = false
- verification_status
- created_at
- updated_at
- deleted_at
```

申请需要本人实名、所属机构或独立服务说明、劳动或合作关系、机构授权书、授权范围和有效期。培训证书记录类型、编号、颁发单位、等级、签发日期和有效期，只作为能力展示或平台风控材料，不标记为国家医疗执业资格。

服务端能力矩阵必须明确禁止咨询师：

- 作出医疗诊断；
- 开具处方；
- 制定个体化医疗治疗方案；
- 实施医疗美容项目；
- 使用医生、主诊医师等受限制身份标签。

咨询师可以提供非医疗的信息说明、流程协助、预约和服务协调。对话触发医疗判断时应转交认证医生。禁止规则必须在服务端操作权限中执行，不能只靠页面文案。

### 机构主体与管理员核验规则

机构认证拆成“机构主体认证”和“账号管理授权”。机构主体以规范化统一社会信用代码作为主要匹配键，不以当前用户既有 membership 作为匹配依据。

主体核验需要：

- 营业执照名称、统一社会信用代码、主体类型、地址、经营状态和法定代表人；
- 医疗机构执业许可登记号、机构名称、地址、法定代表人或主要负责人、有效期、审批机关和诊疗科目；
- 医疗美容一级或二级诊疗科目与拟开放项目范围；
- 人工企业登记和医疗机构登记查询证据。

法人本人申请时核验法人姓名与本人实名一致。经办人非法定代表人时，需要经办人实名、目标机构盖章授权书、授权权限和到期时间。

修复旧 membership 复用逻辑：

1. 根据本次申请的统一社会信用代码查找目标机构；
2. 找到机构时核对名称和医疗许可，不一致则进入人工冲突处理；
3. 未找到时在全部必要核验通过后创建新机构；
4. 只复用属于目标机构且角色、授权主体和申请人一致的 membership；
5. 其他旧 membership 不得被批准、恢复，也不得导致其他机构被标记为已认证。

该匹配、建档和 membership 激活必须与批准操作位于同一事务，并对统一社会信用代码和申请状态加并发保护。

### 状态模型

申请状态扩展为：

```text
DRAFT
PENDING
UNDER_REVIEW
NEEDS_MORE_INFO
APPROVED
REJECTED
```

职业资质状态独立为：

```text
ACTIVE
SUSPENDED
EXPIRED
REVOKED
```

申请是一次审核流程，职业资质是持续状态；不能将同一个 `status` 字段同时表达两者。补件从 `NEEDS_MORE_INFO` 返回 `PENDING`，已有职业资质的复验通过不创建重复职业档案。

批准操作必须在单一事务中：

1. 锁定申请并验证其仍处于可批准状态；
2. 重新校验当前规则安全底线、字段、材料和私有文件状态；
3. 确认所有必要核验项通过且证据仍有效；
4. 执行号码唯一性和跨证照一致性校验；
5. 创建或更新正确的职业档案、机构和关系；
6. 激活职业资质并设置下次复验时间；
7. 写入不可变审核事件；
8. 提交事务后发送通知。

### 有效期、复验和自动降权

资质记录保存 `valid_from`、`valid_until`、`next_reverification_at`、`last_verified_at` 和 `verification_rule_version`。

定时任务按稳定批次处理：

- 到期或复验前 90、30、7 天发送幂等提醒；
- 证照到期时将相关资质置为 `EXPIRED`；
- 复验超期或核验结果不确定时置为 `SUSPENDED`；
- 官方撤销、证据造假或人工确认重大异常时置为 `REVOKED`；
- 失效后回退普通用户工作台，禁止创建新的专业咨询、订单和专业消息；
- 历史消息、订单和咨询保留当时展示快照并标注当前资质状态；
- 补件并复验通过后可从 `SUSPENDED` 或符合策略的 `EXPIRED` 恢复，`REVOKED` 必须走明确的重新申请或申诉流程。

任务以资质 ID、动作类型和计划日期建立幂等键。重复执行不得重复通知、重复事件或覆盖人工处理中的新状态。

身份主动撤销、后台撤销和定时降权共用一个领域服务，以同一方式关闭能力、刷新会话工作身份并使现有登录会话回退普通用户。

### 文件与证据安全

保留当前私有文件所有权和 MIME 签名校验，并增加：

- 服务端真实解码图片或安全解析 PDF；
- 恶意文件扫描；
- 页数、清晰度和完整页检查；
- OCR 仅作为录入辅助，不作为真实性证明；
- 证据访问审计、最小权限和短时下载凭证；
- 按法律、风控和申诉周期配置保留期限，到期安全删除；
- 日志、异常、分析事件和通知中禁止出现完整身份证号及证照号码。

### 数据迁移与兼容

1. 建立认证规则、结构化证照、核验记录、审核事件、职业资质及咨询师档案表。
2. 为现有申请记录其旧规则版本，材料映射为结构化证照草稿，不推定已完成人工核验。
3. 现有 `ACTIVE` 医生、咨询师和机构法人进入迁移宽限期，生成待复验任务；不能在没有证据的情况下批量标记为已核验。
4. 医生档案保留，补充执业范围和备案字段；现有机构关系进入待复核状态。
5. 为现有咨询师生成独立档案草稿，默认非医疗，完成机构授权复验后再开放相应非医疗能力。
6. 机构按统一社会信用代码去重；冲突记录进入人工队列，不自动合并。
7. Flutter 升级期间服务端可短期兼容旧申请读取接口，但新提交必须使用版本化规则。

### 资质核验专项测试

服务端测试必须覆盖：

- 旧机构 membership 与本次统一社会信用代码不一致时绝不复用；
- 相同信用代码并发审批只创建一个机构主体；
- 身份证和统一社会信用代码校验位错误时拒绝；
- 姓名、证照持有人、机构主体或医疗许可不一致时不能批准；
- 审核时私有文件已失效或规则已升级时不能批准；
- 人工必要核验项未完成或证据过期时不能批准；
- 咨询师批准后创建独立档案且永远不获得医疗权限；
- 医生缺少有效执业状态或对应医美备案时不能开放受限能力；
- 到期和复验任务正确暂停、幂等提醒并回退工作身份；
- 撤销与定时降权经过同一个领域服务；
- 旧数据迁移不会把未核验证照标为已验证。

Flutter 测试必须覆盖：

- 根据规则接口动态生成三类表单和材料项；
- 规则版本过期后刷新并保留兼容草稿；
- 身份证、统一社会信用代码和日期即时提示不替代服务端错误；
- 补件、审核中、已暂停、已过期和已撤销状态正确展示；
- 咨询师页面明确显示非医师边界；
- 证照号码、身份证和私有证据不出现在可访问性标签、日志或普通页面中。

### 资质核验分阶段交付

1. 数据库、版本化规则和号码校验基础。
2. 人工核验适配器、审核清单、不可变事件及安全批准事务。
3. 机构匹配修复、咨询师独立档案、医生执业与医美备案字段。
4. 有效期、复验任务、撤销同步和自动降权。
5. Flutter 动态表单、补件流程和持续资质状态展示。
6. 获得官方接口权限后增加自动核验 provider，并用同一契约运行一致性测试。
