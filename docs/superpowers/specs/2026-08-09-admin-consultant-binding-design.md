# 后台咨询师绑定设计

## 目标

管理员可以选择一个正常的普通平台账号和一家机构，在一次操作中授予该账号咨询师职业身份，并创建或恢复其在该机构的已通过咨询师成员关系。

## 范围

- 不创建用户账号，不修改用户密码，不新增数据库表。
- 目标账号必须存在、未注销且平台角色为 `USER`。
- 目标账号可同时保留医生、机构法人及其他职业身份；本次操作只写入 `CONSULTANT` 身份。
- 同一咨询师可以绑定多家机构。
- 用户的咨询师身份和机构成员关系必须在一个事务中完成，避免出现部分成功。

## 服务端设计

新增仅管理员可访问的 `POST /api/admin/identity/consultants`：

```json
{
  "userId": "existing-user-id",
  "institutionId": "institution-id"
}
```

服务在同一事务中：

1. 校验用户存在、未注销、平台角色为 `USER`，并校验机构存在且未删除。
2. 将 `user_roles` 中的 `CONSULTANT` 角色插入或恢复为 `ACTIVE`，不修改任何其他角色。
3. 将 `institution_memberships` 中该用户、机构和 `CONSULTANT` 的关系插入或恢复为 `APPROVED`，写入当前管理员为确认人及确认时间。
4. 返回用户、机构及成员关系标识，供管理端刷新列表。

重复提交同一有效绑定必须幂等，不生成重复关系。已注销账号、管理员账号或无效机构返回明确的业务错误。

## 管理端设计

在“身份与机构关系管理”的“机构成员管理”区域增加“添加咨询师”操作。弹窗包含现有普通用户账号和机构两个必填选择项。提交成功后关闭弹窗并刷新机构成员列表。

原“新增任职关系”保留，用于现有成员管理；它的待审核流程不替代本功能的原子直达已通过绑定。

## 测试

- 服务端覆盖成功授予身份及绑定、多职业身份共存、撤销绑定恢复、重复绑定幂等、已注销账号/管理员账号/不存在机构拒绝。
- Testcontainers 使用固定的 MySQL 8.0.39/InnoDB，并通过生产 `classpath:db/migration` 对空库执行 `B1` baseline migration 后继续执行 V2 至当前最新版本；不得维护测试专用的功能子集 schema。
- 已在共享环境执行的 `V1__init_schema.sql` 必须保持字节不变，避免 Flyway checksum 漂移。`B1` 表达 V1 完成后的等价结构，只为新环境提供安全起点；已有迁移历史的环境会忽略它。
- 并发首次绑定测试必须让两个工作线程分别进入独立事务后再释放开始屏障，并确认使用两个不同的 MySQL 连接；服务方法以默认 `REQUIRED` 加入各自事务。
- 事务中途失败测试在测试管理事务之外触发外键失败，并在服务事务结束后查询数据库，确认角色与成员关系均未留下记录。
- 管理端通过生产构建验证类型与调用契约。
