# Database B33 Baseline Design

## 摘要

以当前完整迁移链执行到 `V33` 后的 MySQL 结构为新基线，新增
`B33__current_schema.sql`。全新空数据库直接执行 `B33`，不再逐条执行
`B26 + V27..V33`；已有数据库继续保留并使用原迁移历史，不回放新基线。
后续结构变更从 `V34` 开始。

本轮只压缩新环境的建库入口，不改变任何业务表含义、不迁移生产数据，
也不修改既有 `B1`、`B26` 或 `V1..V33` 文件。

## 目标

- 将当前 `V33` 最终结构冻结为一个可复现的 schema-only 基线。
- 让新空数据库只执行 `B33` 即获得与旧迁移链一致的业务结构。
- 保证已有数据库忽略 `B33`，继续从其当前版本执行后续增量迁移。
- 明确后续版本从 `V34` 开始，避免基线版本与增量版本混乱。
- 在隔离 MySQL 8.0.39 环境中验证新旧两条路径的结构等价性。

## 非目标

- 不删除、合并或改写任何既有迁移文件。
- 不连接、修复、清理或重置共享开发库和生产库。
- 不把业务数据、测试数据或 Flyway 历史写入基线。
- 不借本次基线调整业务字段、约束或索引。
- 不新增依赖，不拉取新的 Docker 镜像或其他外部资源。
- 不提供通用迁移生成框架；本轮只提交必要快照与验证代码。

## 版本决策

### 基线编号

新文件命名为：

`joysong-server/src/main/resources/db/migration/B33__current_schema.sql`

`B33` 表示该文件等价于执行完所有不高于 `V33` 的既有迁移后的结构。
Flyway 允许同版本的基线迁移 `B33` 与版本迁移 `V33` 共存：

- 全新空数据库选择最新基线 `B33`，不会再执行 `V33`；
- 已有 Flyway 历史的数据库不会执行 `B33`，仍保留原来的 `V33` 记录；
- `B33` 之后的第一个增量迁移必须命名为 `V34__...sql`。

该语义以 Flyway 官方的
[Baseline migrations](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/baseline-migrations)
说明为准。

### 历史文件冻结

下列文件继续保留且不得因本轮修改内容：

- `B1__init_schema.sql`
- `B26__current_schema.sql`
- 所有 `V1..V33`，包括 `V32_1` 与 `V32_2`

保留这些文件可确保已部署数据库的校验和、历史升级路径和回滚调查依据不变。

## B33 内容边界

`B33__current_schema.sql` 是纯结构快照，必须包含 `V33` 最终状态下的：

- 表、列及列顺序；
- 数据类型、长度、精度、NULL 规则和默认值；
- 生成列及表达式；
- 主键、唯一索引和普通索引，包括列顺序与前缀长度；
- 外键和 CHECK 约束；
- 表引擎、字符集和排序规则；
- 结构定义中已有的 `AUTO_INCREMENT` 属性。

基线必须排除：

- 所有业务数据和测试数据；
- `flyway_schema_history` 表及其数据；
- `CREATE DATABASE`、`USE`、GTID、锁表语句和不稳定的导出时间；
- 触发器、存储过程、函数、事件、视图和 `DEFINER`，除非当前真实结构中已明确
  使用这些对象；当前迁移链没有要求新增此类对象。

文件头必须注明：来源为隔离空库执行完整迁移链至 `V33` 后的 schema-only
快照、MySQL 版本为 8.0.39，并提醒后续不得回改 `B33`，只能新增 `V34+`。

## 生成流程

1. 在 `codex/database-baseline-b33` 的独立 worktree 内派生 `WORKTREE_ID`。
2. 使用仓库已缓存的 MySQL 8.0.39；禁止拉取新镜像。
3. 创建名称以 `myapp_worktree_` 开头的全新隔离数据库。
4. 在添加 `B33` 之前执行现有 `B26 + V27..V33` 完整链。
5. 迁移前打印实际数据库 host 和 database name，并校验数据库名边界。
6. 导出 schema-only 内容，排除 Flyway 历史和所有数据。
7. 移除与环境或时间相关的不稳定导出内容，保持定义语义不变。
8. 将规范化结果写入 `B33__current_schema.sql`，不保留临时 dump 或生成脚本。

生成过程不使用共享开发数据库，不执行 drop/reset；任何清理仅针对本 worktree
本次创建且名称满足 `myapp_worktree_` 前缀的隔离资源。

## 迁移行为

### 全新数据库

空数据库迁移到 latest 后，成功历史中应只有：

`33 | SQL_BASELINE | B33__current_schema.sql`

在未来加入 `V34+` 后，则在该记录后顺序执行相应版本迁移。新环境不得再记录
`B26` 或 `V27..V33`。

### 已有数据库

只要数据库已有合法的 `flyway_schema_history`，新增 `B33` 就不应被执行。
例如一个已到 `V32` 的数据库升级到 latest 时，应继续执行 `V32.1`、
`V32.2` 和 `V33`，并保留原数据；之后再执行未来的 `V34+`。

生产部署不需要 `baseline`、`repair` 或重建数据库，也不得为采用新基线而改写
既有 Flyway 历史。

## 验证设计

### 1. 新基线选择测试

先修改现有 `BaselineMigrationIntegrationTest` 的期望，使测试在没有 `B33` 时
失败，再新增基线使其通过。测试应断言全新空库：

- 只记录 `B33__current_schema.sql`；
- 记录类型为 `SQL_BASELINE`、版本为 `33`；
- 不记录 `B26` 与 `V27..V33`；
- Spring/JPA 的现有 schema validation 可以启动通过。

### 2. 新旧路径结构等价测试

在同一个缓存的 MySQL 8.0.39 容器中使用两个独立、合规命名的数据库：

- 新路径：空库直接迁移到 latest，选择 `B33`；
- 旧路径：先将空库迁移到 target `32`，使 Flyway 选择 `B26` 并执行
  `V27..V32`，再迁移到 latest，继续执行 `V32.1`、`V32.2` 和 `V33`。

比较两库的规范化元数据，而不是比较 SQL 文本。比较范围包括：

- 表名、引擎、字符集和排序规则；
- 列顺序、类型、精度、NULL、默认值、extra 与生成表达式；
- 索引唯一性、列顺序、排序方向和前缀长度；
- 外键的列映射、引用目标及 update/delete 规则；
- CHECK 约束及约束表达式。

比较时只忽略 `flyway_schema_history`、数据库名以及安装顺序等非业务差异。
优先扩展现有 `BaselineMigrationIntegrationTest` 和测试辅助方法，避免新增重复的
容器与迁移测试文件。

### 3. 旧库数据兼容测试

保留并运行现有 `DoctorInstitutionProjectFullEditMigrationTest`。该测试继续从
`V32` 历史与代表性数据升级到 latest，验证 `V32.1`、`V32.2`、`V33` 的
兼容性和数据保留；加入 `B33` 后，其历史中不得出现 `B33`。

如现有测试不能明确覆盖上述判断，只做最小断言补充，不复制同类测试。

## 测试与资源约束

- 先运行最小相关迁移测试；失败时只重跑失败类或用例。
- 相关测试通过后，最多运行一次 `mysqlIntegrationTest`。
- 所有 Gradle 命令使用离线模式；Docker 禁止拉取镜像。
- 迁移前输出隔离数据库 host 和 name。
- 测试完成后删除本轮临时 dump、临时数据库和容器，不留下生成文件。
- 不重复执行已通过的相同命令。

## 交付内容

最小改动预计为：

1. 新增 `B33__current_schema.sql`。
2. 更新 `BaselineMigrationIntegrationTest`，覆盖 B33 选择和新旧结构等价。
3. 仅在必要时补强现有 V32 到 V33 的数据兼容断言。
4. 更新面向开发者的迁移说明，明确下一版本从 `V34` 开始；本设计文档可作为
   该说明，不额外创建重复文档。

## 验收标准

- 新空库迁移历史只从 `B33` 开始。
- `B33` 与旧 `B26 + V27..V33` 路径的业务结构元数据完全一致。
- 旧库升级继续执行既有版本迁移且代表性数据不丢失。
- `B1`、`B26`、`V1..V33` 的内容和校验和保持不变。
- 基线不包含业务数据、测试数据或 Flyway 历史。
- 全过程未连接共享数据库，也未下载依赖、镜像或其他资源。
- 后续数据库变更从 `V34` 开始。
