# 旅游地接服务费支付流程重构设计

## 目标

将现有“面诊金 + 尾款 + 平台分账”的医疗支付流程改为单一平台收费流程：平台只向海外用户收取 USD 旅游地接服务费，医院后续直接收取医疗费。用户在下单时选择顾问并立即绑定订单，但只有服务费支付成功后，订单才开放绑定地接人员的履约资料和订单专属沟通。

本设计以最小修改为原则，保留现有通用支付尝试、幂等、回调、主动查单、退款和对账骨架，移除新流程对 Stripe、面诊金、尾款、数量、医疗费平台收款及四方分账的依赖。

活动图见 `design/TRAVEL_GROUND_SERVICE_PAYMENT_WORKFLOW.puml`。

## 已确认业务规则

1. 平台收费名称固定为“旅游地接服务费”。
2. 医生设置医疗套餐优惠前金额，币种固定为 USD。
3. 平台维护原平台分成比例；医生不能直接修改平台比例。
4. 旅游地接服务费按“医疗套餐优惠前金额 × 原平台分成比例”计算，不受优惠券影响，也不乘数量。
5. 用户在下单界面选择顾问；订单创建时立即固化顾问归属，不存在后续自动指派。
6. 支付前不向订单客户端返回顾问标识、履约资料或联系方式，只返回“顾问已绑定”的权限状态。
7. 支付成功后开放绑定地接人员资料和订单专属沟通。
8. 用户在境内、境外都可直接点击支付；客户端不检查 GPS、IP 或国家。
9. 订单创建后 30 分钟未支付自动关闭；单次渠道支付可以更早失效，用户仅可在订单总截止时间前重新发起。
10. 真实/生产渠道仅可由验签回调或服务端主动查单确认支付成功；客户端回跳不能激活服务。显式开启的 `dev` 模拟网关按开发例外直接返回成功。
11. 旅游地接服务费退款仅支持全额退款并进入人工审核。
12. 医院线下收取医疗费；平台不为医疗费创建支付、退款、分账、结算或钱包记录。
13. 首期不建设姓名、护照、航班、酒店等来华资料备案功能。
14. 用户可在地接服务中确认订单完成；完成只结束平台地接履约，不触发医疗确认、医疗尾款、分账或结算。
15. 订单完成后仍允许申请旅游地接服务费全额退款；取消申请或审核拒绝时必须恢复退款前的准确状态。
16. 旅游地接订单处于 `COMPLETED` 时保留退款入口且不可由用户删除；进入 `REFUNDED` 后才恢复删除能力。

## 非目标

- 不处理医院医疗费金额、凭证、退款或纠纷。
- 不提供医疗尾款支付、核销或四方分账。
- 不提供数量购买和服务费优惠券。
- 不提供来华资料备案、护照 OCR、航班识别或酒店管理。
- 不提供支付宝原生 SDK、GPS/IP 判断或强制到达中国后才能支付。
- 不在商户收单参数尚未确定时伪造可用的 Alipay+ 支付结果。
- 不在本次结构迁移中静默删除旧订单数据。

## 金额模型

### 配置来源

- 医生通过现有医生—机构项目配置/变更流程设置 `medicalListPrice`，表示医疗套餐优惠前金额。
- 平台继续通过平台分成策略维护 `platformServiceRate`。
- 金额固定为 USD，比例使用基点存储，`10000` 基点表示 `100%`。

### 服务费计算

```text
travelGroundServiceFeeMinor = roundHalfUp(
    medicalListPriceMinor * platformServiceRateBps / 10000
)
```

订单创建时固化以下快照，后续配置变化不回算历史订单：

- `paymentFlow = TRAVEL_GROUND_SERVICE_ONLY`
- `medicalListPriceMinor`
- `platformServiceRateBps`
- `travelGroundServiceFeeMinor`
- `currency = USD`
- `consultantId` 与顾问公开名称快照

新流程不读取 `quantity`、`couponId`、`consultationFee` 或 `remainingAmount` 计算平台应付金额。

## 订单状态

新流程使用以下业务状态：

```text
PENDING_SERVICE_FEE
  -> SERVICE_ACTIVE
       -> COMPLETED               （用户确认地接服务完成）
  -> REFUND_REVIEW                （SERVICE_ACTIVE 或 COMPLETED 均可进入）
       -> originalStatus          （取消申请或审核拒绝，准确恢复原状态）
       -> REFUND_PROCESSING       （审核批准并提交渠道）
            -> REFUNDED           （渠道确认成功）
```

`CANCELLED` 用于用户主动取消尚未支付的订单、平台人工关闭或订单创建后 30 分钟仍未支付的自动关单。渠道支付尝试在总截止时间前更早过期时，不得单独把订单改为 `CANCELLED`。

新流程中的 `COMPLETED` 只表示旅游地接服务已完成。现有 `CONSULTATION_PAID`、`VERIFIED`、`BALANCE_PAID`、`PENDING_SETTLEMENT` 等状态不能由新流程进入；新流程从 `SERVICE_ACTIVE` 进入 `COMPLETED` 时不得创建 settlement、wallet 或医疗支付记录。为减少一次性重构风险，历史枚举可以在第一阶段保留为不可达兼容值；新页面和新接口不展示或创建这些状态。

## 顾问绑定与信息开放

预约候选列表可以展示用于选择的公开顾问信息，但不能展示私人联系方式。订单创建时服务端校验顾问属于所选医院且状态有效，并立即固化顾问归属。

支付前的用户订单响应：

- `consultantBound = true`
- `serviceActivated = false`
- `consultantDetailsVisible = false`
- `serviceConversationReadable = false`
- `serviceMessagingEnabled = false`
- 不返回 `consultantId`、顾问履约资料或联系方式

支付成功后的用户订单响应：

- `serviceActivated = true`
- `consultantDetailsVisible = true`
- `serviceConversationReadable = true`
- `serviceMessagingEnabled = true`
- 仅返回平台允许公开的地接姓名、机构归属和头像；沟通在平台订单会话内完成，不返回私人电话或站外联系方式

退款状态使用两个独立权限，不以一个 `SERVICE_ACTIVE` 判断代替：

- `REFUND_REVIEW`、`REFUND_PROCESSING`：保留已激活顾问资料与会话历史读取，暂停发送。
- `COMPLETED`：保留顾问允许公开的资料和会话历史读取，停止发送新消息。
- 取消退款或审核拒绝：恢复 `refund.originalStatus`；若恢复为 `SERVICE_ACTIVE` 则恢复发送，若恢复为 `COMPLETED` 则继续只读。
- `REFUNDED`：撤销顾问履约资料，保留已有订单会话历史受控只读。

权限裁剪必须在服务端完成，不能只依靠 Flutter 隐藏组件。

## 平台内沟通

复用现有私信存储，不新建第二套消息系统。`dm_conversations` 增加：

- `conversation_type = DIRECT | ORDER_SERVICE`
- nullable `order_id`
- `ORDER_SERVICE + order_id` 唯一约束

新增 `POST /api/orders/{orderId}/service-conversation`。接口不接受客户端传入的目标用户 ID，而是从订单快照解析订单用户与绑定顾问。订单会话的创建、读取、发送和已读操作都必须重新校验参与者与订单关联，并分别应用权限：

- 当前用户是订单用户或绑定顾问
- 会话的 `order_id` 与订单一致
- 创建新会话与发送消息要求订单处于 `SERVICE_ACTIVE`
- 读取历史与标记已读允许 `SERVICE_ACTIVE`、`COMPLETED`、`REFUND_REVIEW`、`REFUND_PROCESSING`、`REFUNDED`

支付前的普通平台售前咨询可以保留，但它不是订单履约会话。顾问不能通过普通私信接口主动创建与无有效服务关系用户的会话；订单和管理接口也不得在支付前暴露用户电话等私人资料。订单服务会话消息保留平台审计记录，退款审核期间暂停发送，审核拒绝后恢复，退款成功后转为受控只读。

## 支付流程

### 支付合同

- 支付类型：`TRAVEL_GROUND_SERVICE_FEE`
- 支付渠道：`ALIPAY_PLUS`
- 币种：`USD`
- 下一步动作：仅接受服务端返回的受信任 HTTPS 托管收银台地址
- 有效期：不得晚于 `order.createdAt + 30 minutes`；若渠道给出更早有效期则采用更早时间

Flutter 不让用户选择支付类型、渠道或金额。新接口固定业务参数：

```text
POST /api/orders/{orderId}/service-fee-payment-attempts
```

服务端先确认 Alipay+ provider 已配置并启用，再从订单快照取得金额和币种并创建支付尝试。生产环境 Alipay+ 未配置或被关闭时返回 `PAYMENT_PROVIDER_UNAVAILABLE`，不创建本地尝试，也不得写入成功支付。开发阶段允许在 `dev` profile 且 `payment.alipay-plus.simulated-enabled=true` 时装配模拟网关：保留用户点击支付动作，但直接返回带 `simulated-alipay-plus-` 标识的成功结果，不生成收银台跳转；模拟退款只接受同一前缀的模拟支付。

### 30 分钟过期

保留“订单创建后 30 分钟仍未支付则自动关闭订单”，并同步收敛支付尝试：

- 总截止时间为 `order.createdAt + 30 minutes`；截止时订单从 `PENDING_SERVICE_FEE` 进入 `CANCELLED`。
- 无渠道单号的 `CREATED`、`REQUIRES_ACTION` 尝试在到期后进入 `EXPIRED`，不得再创建渠道支付单。
- 已有渠道单号或结果未知的尝试继续按原 provider payment ID / payment request ID 查单，不能仅按本地时间掩盖真实扣款。
- 总截止时间前，若渠道收银台更早明确失效，用户可以创建新尝试；创建前仍须检查进行中或成功支付，避免重复收款。
- 订单已经向用户显示关闭后不得重新激活；渠道晚到成功进入异常扣款补偿退款。

### 支付成功与重复回调

服务端在事务中锁定支付和订单，验证金额、币种、provider payment ID 与订单归属后：

1. 幂等地将支付标记为 `SUCCEEDED`。
2. 将订单从 `PENDING_SERVICE_FEE` 改为 `SERVICE_ACTIVE`。
3. 写入 `serviceActivatedAt`。
4. 开放顾问资料和订单专属沟通。

重复回调不得重复推进状态。若已存在另一笔成功支付，晚到的第二笔成功事件必须记录为资金异常并进入人工退款队列，不能静默忽略真实扣款，也不能重复激活服务。

## Stripe 与 Alipay+

保留：

- `PaymentGateway` 抽象
- 支付尝试与幂等键
- provider 事件收件箱
- 主动查单、退款和对账入口
- HTTPS 托管收银台跳转能力

从新支付链路移除：

- 新订单选择 Stripe 的能力
- Flutter Stripe host 白名单和 Stripe 文案
- Stripe 作为默认/必填生产配置
- Stripe 专属新支付路径

Stripe adapter 暂仅作为显式开启的旧记录兼容能力保留，不能被新订单选择。默认关闭前必须由启动安全门确认不存在仍需查询或退款的 Stripe 支付；若存在则阻止关闭并要求运维显式启用旧 adapter。只有安全门确认无存量责任后才能在后续版本物理删除 adapter。旧订单数据清理必须先备份并核对精确目标，由单独运维步骤执行；结构迁移不得自动删除业务数据。

Alipay+ 商户及收单参数尚未就绪时，生产代码保持 provider 关闭并返回明确不可用状态。真实签名、证书、请求地址和通知格式以最终签约的 Cashier Payment 接口为准。开发模拟网关由 profile 与显式属性双重隔离，不能冒充生产能力或处理真实渠道支付号。

## 退款流程

首期只支持已支付旅游地接服务费的全额退款，`SERVICE_ACTIVE` 和 `COMPLETED` 均可申请：

1. 用户申请后订单进入 `REFUND_REVIEW`，暂停订单服务会话发送。
2. 管理员记录审核人、理由、证据和决定。
3. 用户取消申请或管理员拒绝后，订单恢复退款记录中的 `originalStatus`；原状态为 `SERVICE_ACTIVE` 时恢复沟通发送，原状态为 `COMPLETED` 时保持只读。
4. 批准后仅针对原旅游地接服务费成功支付创建退款项，并进入 `REFUND_PROCESSING`。
5. 渠道确认退款成功后订单进入 `REFUNDED`，撤销顾问履约资料访问和会话发送权限。
6. 渠道结果未知或失败时保持 `REFUND_PROCESSING`；管理后台显示每个退款项的渠道状态、失败码和失败信息，并允许安全、幂等地人工重试。
7. 已有渠道退款单号的失败项优先查询/续办原退款；没有渠道退款单号的失败项使用原幂等键重新发起，已成功项不得重复退款。

医疗费没有平台支付记录，因此不能通过该退款流程申请或执行退款。

## 接口与客户端变化

### 后端

- 修改订单创建请求，移除新流程的 `quantity` 和优惠券输入，保留必填 `consultantId`。
- 提供 USD 旅游地接服务费报价，由服务端计算并返回。
- 订单响应增加显式权限字段并按支付状态裁剪顾问信息。
- 增加固定类型的服务费支付尝试接口。
- 增加订单专属服务会话接口并为消息操作增加订单权限校验。
- 将服务费退款切换为人工审核；禁止新流程创建 `BALANCE` 支付和四方结算。
- 复用现有确认完成接口处理旅游地接订单，但新流程只写入 `COMPLETED/completedAt`，不进入医疗结算。
- 管理端退款接口返回退款项及渠道错误详情，并提供处理中的失败退款人工重试接口。

### Flutter

- 下单页保留顾问选择，删除数量、面诊金、尾款和服务费优惠券展示。
- 展示 USD 旅游地接服务费及“医疗费到院直接向医院支付”说明。
- 支付前显示绑定占位卡，不显示顾问履约资料或地接沟通入口。
- 支付成功后显示地接资料卡和订单专属沟通入口。
- 服务中显示“确认地接服务完成”；完成后资料与沟通历史可读、消息只读，并仍可申请全额退款。
- 支付页只展示 Alipay+、USD 金额、支付尝试有效期和过期重试。
- 删除 Stripe、面诊金、尾款和医疗费平台支付文案与入口。

### 管理端

- 在现有医生项目配置/变更流程中支持医生维护医疗套餐优惠前金额。
- 订单、支付和退款页面使用“旅游地接服务费”语义。
- 管理员执行全额退款审核，并能查看渠道退款处理状态。
- 管理员可查看失败退款项的渠道错误并安全重试；重试后刷新最新状态。
- 新流程不显示分账、钱包或医疗尾款操作。

## 数据库迁移原则

新增迁移，不修改已经执行的历史迁移：

- 订单增加支付流程、金额快照、比例快照和服务激活时间。
- 会话增加类型和订单关联，并建立订单服务会话唯一约束。
- 支付类型允许 `TRAVEL_GROUND_SERVICE_FEE`。
- 新流程不自动生成 settlement 或 wallet 数据。

迁移测试必须使用按 worktree 隔离的新空数据库，并在迁移前输出解析后的数据库主机和数据库名。除空库迁移外，还要先迁移到旧版本、写入代表性旧订单，再升级到最新版本并断言旧行仍保留且标记为 `LEGACY_MEDICAL`。旧订单删除不放入结构迁移。

## 最低验收场景

1. 用户未选择顾问不能下单；选择后顾问立即绑定。
2. 服务费严格按医生设置的优惠前金额和平台比例快照计算，USD 舍入一致，无数量和优惠券影响。
3. 支付前用户订单响应不包含顾问 ID、履约资料或联系方式，服务会话接口返回无权限。
4. 真实/生产支付成功只能由验签回调或主动查单确认，并且只激活一次服务关系；显式开启的 `dev` 模拟网关可直接返回带模拟标识的成功结果。
5. 支付成功后用户可以查看允许公开的地接资料并进入对应订单的专属会话。
6. 普通私信不能绕过订单支付状态创建订单履约关系。
7. 订单创建后 30 分钟未支付自动取消；渠道尝试更早失效时，仅允许在订单总截止时间前创建新尝试。
8. 新流程不能创建 `BALANCE` 支付、医疗费退款、四方分账或钱包流水。
9. 退款申请必须人工审核；拒绝恢复服务，渠道退款成功后撤销服务权限。
10. Flutter 和管理端不再出现面诊金、尾款、数量或 Stripe 新支付入口。
11. 生产环境 Alipay+ 未配置时明确显示支付渠道暂不可用，不产生模拟成功记录；开发环境显式开启时，点击支付可立即得到带模拟标识的成功结果。
12. 本次变更不新增来华资料备案入口、接口或数据表。
13. `SERVICE_ACTIVE` 可确认地接服务完成；结果为 `COMPLETED`，且不会生成医疗确认、尾款、结算、分账或钱包数据。
14. `COMPLETED` 仍可申请全额退款且不可删除；取消申请或审核拒绝后准确恢复 `COMPLETED`，会话保持只读。
15. 渠道退款失败不会伪装成功；后台能查看失败详情并幂等重试，已成功退款项不会重复执行。

## 推进边界

第一阶段先完成订单金额语义、支付状态、订单级 30 分钟支付时限和退款安全边界；第二阶段完成订单专属沟通权限；第三阶段完成 Flutter、管理端及文档清理。Alipay+ 真实渠道联调在商户与收单参数可用后进行；仅本地 `dev` profile 可显式启用模拟成功，生产环境始终禁止。
