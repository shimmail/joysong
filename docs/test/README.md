# 全角色最小联调测试总流程

本文是 `docs/test` 唯一需要顺序执行的测试清单。目标不是穷举所有生命周期分支，而是用一套共享数据跑通：

`普通用户注册 → 法人创建机构 → 医生/顾问入驻 → 项目上架 → 用户下单 → 支付 → 完成 → 评价`

各角色分册只补充该角色独有的字段、页面和断言；注册、公开浏览和订单状态只在普通用户分册详细描述，不再由多个角色重复测试。

### 1.2 执行规则

1. 只按第 5 节执行 `SMOKE-00` 至 `SMOKE-08`。
2. 同一账号、申请、机构、项目和订单全程复用，禁止在角色分册重复创建。
3. 每一步只保存“操作成功 + 核心状态 + 一个关键页面”的最小证据。
4. 第 7 节的边界场景默认不执行；主链路失败或专项回归时再选取。
5. 主链路结果使用 `通过 / 失败 / 阻断 / N/A`，不得用“未观察到问题”代替结论。

## 2. 环境和共享数据

### 2.1 开始前确认

- 使用隔离测试环境和隔离数据库，记录 App、服务端和管理端版本。
- 测试短信白名单或验证码桩可用；如环境固定验证码，统一使用 `123456`。
- 对象存储允许上传带 `TEST SAMPLE / 仅用于测试` 水印的虚构材料。
- 测试支付或模拟支付可用；禁止连接生产商户或真实扣款。
- 所有预约时间至少晚于当前时间 2 天。
- 不上传真实证件、真实执照、真实头像或真实患者资料。

任一隔离条件不满足时，停止会写入身份、订单或支付数据的步骤，并记录环境阻断。

## 3. 最小状态与职责

### 3.1 本轮只关注的状态

| 对象 | 主链路状态 |
|---|---|
| 账号 | 未注册 → `ACTIVE` |
| 专业身份申请 | `PENDING` → `APPROVED` |
| 专业角色 | 无 → `ACTIVE` |
| 医生/顾问机构关系 | `JOIN/PENDING` → `JOIN/APPROVED` |
| 平台项目 | 待审 → 已批准/可用 |
| 机构项目 | `CREATE/PENDING` → 已批准/可下单 |
| 订单 | 已创建 → 支付成功/`SERVICE_ACTIVE` → 已完成 → 已评价 |

补充规则：待审专业身份由管理员 `APPROVE` 或 `REJECT`；生效专业身份由管理员 `REVOKE`。本轮只执行三次 `APPROVE`，`REJECT` 和 `REVOKE` 留到专项回归。

### 3.2 审核职责

| 对象 | 发起人 | 审核人 |
|---|---|---|
| 法人、医生、顾问身份 | 对应普通用户 | `A-01` |
| 医生/顾问加入 `I-01` | `D-01` / `C-01` | `L-01` |
| `P-01` 平台项目 | `D-01` | `A-01` |
| `IPJ-01` 机构项目 | `D-01` | `L-01` |

主链路禁止由发起人审批自己的申请，也不使用管理员兜底接口替代法人正常审核。

## 4. 测试开始状态

执行前确认或清理本轮测试编号对应的数据，使起点满足：

- `A-01` 为可登录的 `ACTIVE + ADMIN`；
- `L-01`、`D-01`、`C-01`、`U-01` 尚未注册；
- 不存在同名 `I-01`、`P-01`、`IPJ-01`；
- 不存在使用本轮四个普通账号创建的未结束身份申请；
- 测试支付环境没有复用旧订单回调。

如环境不能恢复到该起点，使用新的测试编号或手机号，不要直接修改共享开发数据库凑状态。

## 5. 九步最小冒烟主链路

### `SMOKE-00` 环境与管理员

1. 记录三个应用版本、测试数据库标识、短信方式和支付方式。
2. `A-01` 登录独立管理端。
3. 打开身份申请、平台项目和订单管理列表，确认接口可用。

通过：`A-01` 为 `ACTIVE + ADMIN`，管理功能可正常打开。

### `SMOKE-01` 注册共享普通账号

1. 用 `U-01` 完成手机号注册、密码登录、验证码登录和一次昵称修改。
2. 分别注册 `L-01`、`D-01`、`C-01`，只检查自动登录和普通用户首页。
3. 记录四个 userId。

通过：四个账号均为 `ACTIVE + USER`；尚无任何专业权限；任一普通用户令牌均不能访问管理员能力。注册字段和页面断言见[普通用户分册](user-full-chain-manual-test-20260829.md)。

### `SMOKE-02` 法人和机构

1. `L-01` 按[法人分册](legal-representative-full-chain-manual-test-20260829.md)提交法人身份及 `I-01` 数据。
2. `A-01` 直接批准本次申请。
3. 检查法人角色、`I-01`、法人任职和机构钱包在同一结果中初始化成功。
4. `L-01` 编辑一组核心机构资料，`U-01` 从公开入口查看。

通过：`L-01` 能管理 `I-01`；`U-01` 能看到更新后的公开字段，看不到法人私密材料。

### `SMOKE-03` 医生入驻机构

1. `D-01` 按[医生分册](doctor-full-chain-manual-test-20260829.md)提交医生身份及五份测试材料。
2. `A-01` 直接批准，`D-01` 完成最小公开档案。
3. `D-01` 申请加入 `I-01`，`L-01` 批准。
4. `U-01` 查看 `I-01` 医生列表和 `D-01` 公开详情。

通过：医生角色、医生档案和钱包已初始化；关系为 `JOIN/APPROVED`；私密材料不公开。

### `SMOKE-04` 顾问入驻机构

1. `C-01` 按[顾问分册](consultant-full-chain-manual-test-20260829.md)提交顾问身份及三份测试材料。
2. `A-01` 直接批准。
3. `C-01` 申请加入 `I-01`，`L-01` 批准。
4. `U-01` 查看 `I-01` 顾问列表或预约候选。

通过：顾问角色和钱包已初始化，不错误创建医生式专业档案；`C-01` 出现在 `I-01` 的公开候选中。

### `SMOKE-05` 项目可售

1. `D-01` 提交平台项目 `P-01`，`A-01` 批准。
2. `D-01` 在 `I-01` 下基于 `P-01` 提交 `IPJ-01`，`L-01` 批准。
3. `U-01` 查看项目公开页和价格。

通过：`IPJ-01` 与 `D-01` 绑定并可下单；机构价/医生价为 `220.00 USD`；不检查任何分账字段。

### `SMOKE-06` 用户创建订单

1. `U-01` 浏览 `I-01`、`D-01`、`C-01` 和 `IPJ-01`。
2. 选择 `I-01 + IPJ-01 + D-01 + C-01`，以至少未来 2 天的预约时间创建 `O-01`。
3. 记录订单详情和服务端返回。

通过：订单快照中的机构、项目、医生、顾问、预约时间、`220.00 USD` 均与选择一致；`U-01` 只能看到本人订单。

### `SMOKE-07` 支付与角色可见范围

1. 仅通过明确的测试/模拟支付让 `O-01` 进入 `SERVICE_ACTIVE`。
2. `U-01` 查看本人订单，`D-01` 查看本人医生订单，`A-01` 查看全局订单。
3. 检查 `C-01` 已写入订单分配快照。

通过：服务端支付事实成立，三个现有订单视角范围正确；浏览器返回页不能单独作为支付成功证据。

已知限制：顾问尚无独立订单工作台和完整履约入口。因此本步可以判定“核心交易冒烟通过”，但不得写成“用户、医生、顾问三方 GUI 履约完整闭环”。

### `SMOKE-08` 完成与评价

1. 按当前可用规则由 `U-01` 确认完成，或等待系统把 `O-01` 置为可评价的完成状态。
2. `U-01` 提交 `USER-REVIEW-001`。
3. 刷新用户订单和对应公开评价区域。

通过：只有完成订单可评价；本单仅成功评价一次；评价绑定 `O-01` 的真实机构、医生和项目。

## 6. 主链路通过标准

满足以下条件即可将本轮“最小联调主链路”标记为通过：

- `SMOKE-00` 至 `SMOKE-08` 均有结论，除明确的 `SCOPE-01` 外没有跳步；
- 五个账号、三个专业身份、两个机构关系、两个项目对象和一笔订单 ID 可互相追溯；
- 专业私密材料没有出现在普通用户公开接口或页面；
- 发起人与审核人符合第 3.2 节；
- 价格和币种来自服务端订单快照；
- 已知的顾问工作台限制被如实记录，没有冒充三方完整履约通过。

模拟支付通过只代表测试链路可跑通，不代表真实 Alipay+ 生产链路已放行。

## 7. 可选回归，不纳入默认主链路

只在相关模块改动、主流程失败或发布前专项验收时选择执行：

| 专项 | 内容 | 主要分册 |
|---|---|---|
| 身份异常 | 驳回、重提、重复提交、待审取消诉求 | 法人/医生/顾问/管理员 |
| 多管理员 | `A-02`、最后管理员保护、并发审批、审计 | 管理员 |
| 多机构 | 第二机构、跨机构越权、同角色多机构切换 | 法人/医生/顾问 |
| 关系退出 | `LEAVE` 撤回、驳回、批准、重新加入 | 法人/医生/顾问 |
| 账号状态 | 暂停、恢复、公开入口过滤、旧令牌失效 | 管理员与对应角色 |
| 身份终止 | 管理员 `REVOKE`、重新认证、不自动恢复旧关系 | 管理员与对应角色 |
| 账号注销 | 无商业数据专用账号、`ERASED`、原手机号重新注册 | 普通用户/管理员 |
| 订单健壮性 | 重复点击、并发、失败支付、回调幂等、重复评价 | 普通用户/管理员 |
| 项目扩展 | 加入已有机构项目、资料更新、第二项目 | 医生/法人/管理员 |
| 完整界面矩阵 | 中英文、Android/iOS、多宽度、大字体和异常文案 | 各角色 |

执行专项时新建独立测试编号和数据，不修改本轮 `O-01` 的已完成证据。

## 8. 最小页面排版检查

本轮只在一个基准设备和一种语言下检查四类关键页面：

1. 注册/登录；
2. 身份申请和材料上传；
3. 机构、医生、顾问及项目公开详情；
4. 订单确认、支付结果、完成和评价。

每页只检查：无遮挡、无溢出、按钮可点击、错误提示可读、返回后状态不丢失。中英文、双平台和多尺寸完整组合属于第 7 节可选回归。

## 10. 维护规则

- 新增主流程步骤前，先确认它是否已由现有角色步骤覆盖。
- 同一业务事实只在一个文档详细描述，其他文档使用相对链接引用。
- 不把拒绝、撤回、暂停、撤销、注销或并发用例重新塞回默认冒烟链路。
- 功能实现变化时先更新本清单和对应角色分册；状态模型变化时再更新 UML 源码。
- 本目录只维护 Markdown 和 PlantUML 源码。
